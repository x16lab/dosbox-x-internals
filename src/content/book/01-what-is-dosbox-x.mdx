# Chapter 1 — What Is DOSBox-X and Why Does It Exist? {#chapter-1-what-is-dosbox-x-and-why-does-it-exist}

In 1981, IBM introduced the Personal Computer. Few engineers could have predicted that decades later, developers would still be running 16-bit software written for Intel's 8088 processor on ARM laptops and multi-core workstations. DOSBox-X exists because software rarely dies — it merely waits for someone to emulate the hardware it once called home.

This chapter is not about DOSBox-X's source code. It's about the forty years of hardware, operating system, and industry history that made DOSBox-X necessary — and, more specifically, that made a *fork* of an already-existing emulator necessary. By the end of it, you should understand not just that DOSBox-X emulates a CPU, memory, BIOS, PIC, PIT, VGA, DMA, DOS kernel, sound hardware, and storage controllers, but *why* each of those pieces had to exist on the original hardware in the first place — because every one of them is a direct consequence of a decision IBM, Intel, or Microsoft made decades ago, usually for reasons that had nothing to do with elegance.

There's a lot of ground between those two points. Before setting out, it helps to have the timeline of that journey laid out in front of you, even in rough form — a set of waypoints to recognize as they go by, rather than a map you need to memorize:

```text
1981   IBM PC
1983   PC/XT
1984   IBM AT (286)
1987   VGA introduced
1990   Windows 3.0
1995   Windows 95
1998   Windows 98
2001   Windows XP  (no DOS underneath, consumer DOS compatibility breaks)
2002   DOSBox founded
2011   DOSBox-X forks from DOSBox
2026   this book
```

Hold that timeline loosely — the sections ahead will fill it in a stretch at a time, starting with the machine IBM actually shipped in 1981.

## 1.1 The IBM PC (1981) {#the-ibm-pc-1981}

The IBM PC was not a clean-sheet design. It was an assemblage of off-the-shelf and semi-custom parts chosen under time pressure, and nearly every quirk DOSBox-X has to reproduce today traces back to a specific component IBM picked in 1980–81:

- **The Intel 8088 CPU** — a cost-reduced variant of the 8086 with an 8-bit external data bus but the same 16-bit internal architecture and the same segmented memory model: a 20-bit address space (1 MB) accessed through 16-bit segment:offset pairs. This segmentation — not paging, not a flat address space — is the single architectural decision that echoes loudest through DOS software history. It's why far and near pointers are different types, why "huge" pointers had to exist as a compiler-level workaround, and why so much DOS-era code (including, notably, the kind of MSC-compiled 16-bit binaries you might spend months reverse engineering) is inseparable from its segment layout.
- **The 8259 Programmable Interrupt Controller (PIC)** — handled hardware interrupts (keyboard, timer, disk) and gave the system a fixed, small vector table of things the CPU could be asynchronously told to care about.
- **The 8253 Programmable Interval Timer (PIT)** — generated the system clock tick (roughly 18.2 times a second on the original PC, a number derived from dividing the PC's 14.31818 MHz crystal down through the PIT) and drove the PC speaker.
- **The 8237 DMA controller** — let peripherals move data to and from memory without CPU involvement, later repurposed heavily by Sound Blaster-compatible cards for audio streaming.
- **CGA, and later EGA and VGA graphics adapters** — each generation added registers and modes without removing the old ones, so "VGA-compatible" by the early 1990s meant compatible with roughly a decade of accumulated graphics hardware history, not a single clean spec.

None of these components were designed as a coherent whole. They were wired together, given a BIOS to initialize them, and left for software to sort out the details — which is exactly why an emulator faithful to DOS software has to model each one individually rather than treating "the PC" as a single abstract machine. There is no such thing as "the PC" in the singular; there's a bus full of chips, each with its own register-level contract, and DOS-era software talks to all of them directly.

```text
   8088  ---+
   8259  ---|
   8253  ---|---->  "The IBM PC"
   8237  ---|
   VGA   ---|
   BIOS  ---+
```

Ironically, the IBM PC became the platform DOSBox-X has to emulate not because IBM tightly controlled it, but because the industry learned how to reproduce it. IBM's BIOS was copyrighted, but its behavior wasn't — and clean-room reimplementations of that BIOS (Compaq's being the most consequential) let other manufacturers build machines that ran the same software without infringing IBM's code. By the late 1980s, "IBM compatible" had become a de facto standard implemented by hundreds of manufacturers, most of whom had never licensed anything from IBM at all. This matters for an emulation project specifically: the "IBM PC" that DOS software actually targets, and that DOSBox-X actually emulates, was mostly not built by IBM. It was a moving industry consensus about register-level behavior — which is also why that consensus was never perfectly uniform, and why period software occasionally assumes hardware quirks from one clone vendor that don't hold on another.

## 1.2 The Rise of MS-DOS {#the-rise-of-ms-dos}

IBM needed an operating system quickly, and licensed what became PC-DOS/MS-DOS from Microsoft (itself built from Seattle Computer Products' 86-DOS). By modern standards, MS-DOS provided remarkably little abstraction over the underlying hardware: no memory protection, no preemptive multitasking, no device abstraction layer worth the name. It provided a filesystem (FAT), a rudimentary set of interrupt-based system calls (chiefly `INT 21h`), and got out of the way.

That "getting out of the way" is the crucial detail. DOS did not mediate access to hardware the way a modern OS does. A DOS program that wanted to draw pixels didn't ask an OS graphics service to do it — it wrote directly to VGA registers and video memory at segment `0xA000`. A program that wanted low-latency sound programmed the Sound Blaster's DSP directly, or drove the PC speaker's timer channel by hand. DOS supplied file I/O and a few conveniences; everything performance-sensitive went straight to the metal.

## 1.3 Why DOS Software Was Tied to Hardware {#why-dos-software-was-tied-to-hardware}

This is the fact that makes DOS emulation categorically different from, say, emulating a Java virtual machine or reproducing a POSIX environment. A DOS game from 1993 isn't targeting "DOS" as an abstract platform — it's targeting DOS *plus* a specific, if loosely standardized, hardware profile: an x86 CPU of some minimum generation, a VGA-compatible adapter with known register semantics, an 8253 PIT for timing loops, and, if it wanted sound, a Sound Blaster or Sound-Blaster-compatible card at a specific I/O base and IRQ/DMA configuration (the infamous `SET BLASTER=A220 I5 D1 T4` environment variable that an entire generation of PC gamers memorized).

This is why perfect DOS emulation requires emulating hardware, not an operating system. There's no API boundary to reimplement — the "API" is the hardware's register map. An emulator that gets the PIT's timing behavior slightly wrong will make a game's frame-pacing loop run too fast or too slow, even though nothing about "DOS" per se has changed. This single fact is the organizing principle of nearly every device-emulation chapter later in this book: DOSBox-X isn't approximating an operating system; it's reconstructing a specific PC architecture closely enough that software which assumes direct hardware access can't tell the difference.

## 1.4 What Does It Mean to "Emulate" a Computer? {#what-does-it-mean-to-emulate-a-computer}

Here's a question worth sitting with before this chapter moves on: if two different emulators both run the same 1993 DOS game, and both produce the same picture on screen, are they equally correct?

The honest answer is *maybe not*, and the gap between those two possible emulators is exactly what separates "emulation" from a much easier problem it's often confused with. Suppose one of the two programs isn't emulating a PC at all — it's simply reading the game's original graphics assets and redrawing the same scene using modern code, understanding nothing about VGA registers, DOS interrupts, or x86 instructions. That program might reproduce the opening screen perfectly and still be useless the moment the game does something even slightly unusual — reads a joystick in a way the reimplementation didn't anticipate, times an animation off the PC speaker's frequency, or relies on a CPU quirk nobody thought to reverse-engineer. It's a **simulation** of that one specific behavior, not an emulation of the machine underneath it. An emulator, in the stricter and more useful sense this book means by the word, doesn't know or care what the game is *trying* to do. It only knows how to faithfully reproduce what the original hardware would have done, instruction by instruction and register by register, and trusts that if the hardware behavior is right, whatever the software does with that hardware will come out right too — without the emulator ever needing to understand the software's intent at all.

That distinction is why @chapter(what-is-dosbox-x)'s argument about DOS software's tight hardware coupling isn't just historical color — it's the reason DOSBox-X has to commit to the harder, more general strategy rather than the easier, more targeted one. A general-purpose reimplementation strategy (asset extraction, behavioral reproduction, game-specific patches) works fine for a small, fixed catalog of well-known titles and falls apart the moment you point it at software nobody has specifically studied. A genuine hardware emulator, correctly built once, runs software nobody involved in writing the emulator has ever seen or tested — which is precisely the property that makes an emulator worth building at all, and precisely the property this book is going to spend the rest of its length explaining how DOSBox-X achieves.

Two ideas from that stricter definition are worth previewing here, because they'll recur, in progressively more concrete form, all the way through this book:

**Emulation is mostly about faithfully tracking state, not performing computation.** A real 8253 PIT doesn't "compute" anything interesting — it counts down and changes its output pin's level at the right moments. Emulating it correctly means keeping a piece of software-visible state (a counter, a mode, an output level) that changes at exactly the moments the real chip's would have. Multiply that by every chip on a real motherboard — the CPU's registers, the PIC's interrupt-request bits, the VGA card's palette and mode registers, the DMA controller's transfer counters — and "emulating a PC" starts to look less like one big program and more like a large collection of small state machines, each modeling one real chip, updated in response to the same events (an I/O port write, a clock tick, a completed disk transfer) that would have updated the real chip. That's not a metaphor DOSBox-X's design merely resembles — it's close to literally how the source tree is organized, as the next chapter will show in detail: one module per chip, each owning its own state, each updated by the same kinds of triggers a real chip would respond to.

**There is more than one legitimate way to execute the guest CPU's instructions, and the choice is a pure engineering tradeoff, not a correctness question.** You could read the guest program's bytes one instruction at a time, decode each one, and immediately carry out its effect — simple to build, easy to get right, but paying the cost of decoding the same instruction over and over if a loop runs it a thousand times. Or you could translate a whole stretch of guest instructions into real, native machine code once, cache that translation, and let the host CPU run it directly on every subsequent pass through the same loop — considerably faster in the common case, considerably more work to build and to keep correct when the guest code changes underneath you. Both strategies, done correctly, have to produce bit-for-bit identical results for the same guest program; neither one is "more accurate" than the other, because accuracy here is measured against the real hardware's behavior, not against how the emulator internally gets there. DOSBox-X actually implements both, side by side, letting you choose — a decision this book will unpack in full once Part II gets to the CPU cores themselves.

If you take one thing from this section into the rest of the book, let it be this: everywhere you see DOSBox-X modeling something that looks, at first glance, oddly literal — a struct field for a chip's interrupt-request bits, a table entry for one specific I/O port, a flag that's cleared and set at exactly the moments a datasheet says it should be — that literalism isn't incidental detail. It's the entire strategy. The next chapter picks this up concretely, mapping out exactly how DOSBox-X's source tree divides "the PC" into the collection of independent, chip-shaped modules this section has just described in the abstract.

## 1.5 The End of DOS and Windows 9x {#the-end-of-dos-and-windows-9x}

Through the Windows 3.x era, DOS was still there, underneath, as a bootstrap layer. Windows 95, 98, and Me continued this arrangement: a real-mode DOS kernel (MS-DOS 7.x) booted first, then Windows loaded on top of it, and DOS applications could still, with varying degrees of success, run in a virtual 8086 mode session or drop to a real DOS prompt entirely.

Windows XP, released in October 2001, changed this permanently for consumer Windows. Built on the Windows NT kernel rather than the DOS/9x lineage, XP had no real DOS underneath it — only NTVDM, a virtual machine layer that could run *some* DOS software but had no direct access to real hardware and increasingly poor compatibility with anything that touched sound or graphics registers directly, exactly the category of software described in the previous section. Games and utilities that had worked, unmodified, since the early 1990s began failing outright on the operating system that PC users were now expected to run.

This is the gap DOSBox was built to fill.

## 1.6 The Birth of DOSBox (2002) {#the-birth-of-dosbox-2002}

DOSBox was created by two Dutch programmers, Peter "Qbix" Veenstra and Sjoerd "Harekiet" van der Berg, who had noticed DOS compatibility eroding as far back as Windows 2000, and set out to build a replacement environment for DOS software rather than rely on Windows' shrinking native support. The first public version, DOSBox 0.1, was released on January 31, 2002, with the project uploaded to SourceForge for wider beta testing that July.

Critically, DOSBox was not built as a general-purpose "run any DOS program" tool in the abstract — its founders' stated goal was bringing DOS gaming back to a Windows platform that had abandoned it. That focus shaped everything about the project's priorities for the next two decades: DOSBox aimed to run the corpus of 1990s DOS games as reliably and simply as possible, using SDL for cross-platform portability, and largely treated correctness as a means to that end rather than an end in itself. Where accurately modeling a piece of hardware and simply special-casing a game's behavior led to the same practical outcome — the game runs — the pragmatic fix usually won.

That pragmatism is not a criticism. It's the reason DOSBox succeeded as fast and as broadly as it did: it solved the actual problem nearly the entire remaining DOS-gaming audience had, with minimal configuration burden. It also, as an inevitable consequence, left an opening for a different kind of project.

## 1.7 Limitations of Original DOSBox {#limitations-of-original-dosbox}

By the mid-to-late 2000s, DOSBox's design tradeoffs had calcified into real limits for anyone whose interests extended past "make popular DOS games playable":

- **Narrow OS scope.** DOSBox emulates a DOS environment, full stop. Running Windows 3.x, and especially Windows 95/98/Me, was at best partially supported and often outright impractical — yet a huge amount of PC software history (and PC hardware-behavior history) lived in that Windows 9x/DOS-hybrid era, not purely in DOS.
- **Kludge-oriented compatibility.** Because the guiding metric was "does the game run," some emulation shortcuts prioritized specific popular titles' expectations over general hardware fidelity. That's a perfectly rational choice for a gaming-focused emulator, but it works against anyone trying to use the emulator as a *reference* for how real hardware behaved.
- **Upstream development friction.** DOSBox's SourceForge-hosted SVN repository and small, focused maintainer team meant that substantial, non-gaming-motivated patches — deeper hardware accuracy work, PC-98 support, expanded Windows compatibility — were slow to land or unlikely to be accepted at all, since they fell outside the project's core mission.
- **No debugging/development affordances.** DOSBox was built to be *played*, not built to be a platform other developers could instrument, extend, or use as a reverse-engineering aid.

None of this was a flaw in DOSBox's execution of its own goals. It was a mismatch between DOSBox's goals and a different set of goals that a growing number of users — retrocomputing enthusiasts, Windows 9x preservationists, PC-98 users outside the Western DOS mainstream, and developers who wanted an accurate, instrumentable PC platform — increasingly wanted served.

## 1.8 Emergence of DOSBox-X {#emergence-of-dosbox-x}

DOSBox-X began as a fork of the original DOSBox project around mid-2011, started by Jonathan Campbell, who wanted to make broad emulator changes — many of them not related to gaming — without being dependent on upstream acceptance in a project whose central focus remained DOS games. As the project's own documentation puts it plainly: DOSBox's code contained plenty of "somewhat accurate" behavior patched with kludges specifically to make certain games run, rather than code that modeled what real DOS systems actually did — and that was fundamentally at odds with what Campbell wanted to build.

Rather than fighting that mismatch upstream, forking sidestepped it entirely. A fork doesn't require consensus from the original maintainers about what the project is *for*; it just requires a public repository and someone willing to keep committing to it. Over the following years, DOSBox-X absorbed not only Campbell's own accuracy- and Windows-9x-motivated work but also code and ideas from several sibling DOSBox derivatives — DOSBox SVN Daum, DOSBox ECE, DOSBox Staging, and vDosPlus, with DOSVAX/DOSVAXJ3 credited in some of the project's own documentation as well[^1] — making DOSBox-X less a single fork and more a confluence point for most of the DOSBox family tree's accuracy- and compatibility-oriented work.

## 1.9 Goals of DOSBox-X {#goals-of-dosbox-x}

By the time DOSBox-X matured into the project reflected in this book's source tree, its goals had crystallized around several threads that distinguish it clearly from upstream DOSBox:

- **A complete DOS environment**, not just a DOS-games launcher — full command-line utilities, device driver support, and configuration flexibility aimed at people who want to actually *use* DOS, not just point it at one executable.
- **Substantially better Windows 3.x/9x/Me support** — treating the DOS-to-Windows-9x continuum as a single lineage worth emulating properly, rather than drawing a hard line at "DOS software only."
- **PC-98 support** — NEC's PC-98 platform was a parallel, largely IBM-PC-incompatible personal computer architecture that dominated the Japanese market for most of the DOS era. DOSBox-X emulates it as a genuinely separate hardware target, not a variant of the IBM PC path — a scope decision essentially unthinkable for a project narrowly focused on Western DOS gaming.
- **Improved hardware accuracy** as a goal in its own right, not merely as a side effect of chasing game compatibility — motivated as much by preservation and research use cases as by getting any particular title to run.
- **A platform for development and instrumentation** — an integrated debugger, save states, extensive logging, and a configuration surface broad enough to make DOSBox-X usable as a research and reverse-engineering tool, not only an end-user player.

That last goal is the one most relevant to this book, and to the kind of work that emerges when studying legacy software at the machine level — cross-referencing binary reconstructions against period-accurate hardware timing, tracing interrupt dispatch, verifying VGA register behavior, and understanding the subtle interactions between software and emulated hardware. DOSBox-X’s willingness to be more than a games launcher is precisely what makes its source tree worth studying architecturally, rather than simply treating it as a black box.

It's worth stating plainly how far that use case now extends. Today, DOSBox-X gets used not only for playing games but for digital preservation, reverse engineering of DOS-era binaries, compiler archaeology, operating-system research, and recovering software whose original hardware no longer exists or is no longer economical to keep running. None of that was the emulator's founding purpose — DOSBox's founders wanted playable games, and DOSBox-X's founder wanted broader accuracy and platform scope — but accuracy as a goal in its own right turns out to generalize well past gaming, into exactly the kind of forensic, register-level work the rest of this book is concerned with.

## 1.10 What This Book Covers {#what-this-book-covers}

The chapters that follow trace DOSBox-X from the outside in. @chapter(dosbox-x-architecture) lays out the emulator's modular architecture — the major components and how they're allowed to talk to each other — before @chapter(main-loop-and-event-scheduler) opens the source tree itself and follows execution from `main()` through SDL initialization into the event scheduler, the mechanism that decides, at every instant, which of the many hardware subsystems introduced in this chapter gets to run next. Every one of those chapters is, in a real sense, an answer to a question this chapter has already set up: given that DOS-era software assumes direct, unmediated access to a specific and idiosyncratic set of 1980s-vintage hardware, what does it take to convince that software the hardware is still there?
