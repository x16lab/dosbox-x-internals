# Chapter 4 — The Main Loop and Event Scheduler {#chapter-4-the-main-loop-and-event-scheduler}

*(Source references below are against `joncampbell123/dosbox-x`, commit `192c1756`, cloned 2026-07-25. File/line numbers will drift as the project moves; treat them as coordinates into a moving target, not fixed citations.)*

## 4.1 The Execution Problem {#the-execution-problem}

Chapter 3 closed by pointing ahead to the main loop and event scheduler as the missing piece — the machinery that decides exactly when to stop the CPU so a device can act, once the timing model it established is in place. This chapter traces that machinery from `main()` outward. Once the emulated machine is constructed and its timing domains are live (Chapter 3), DOSBox-X's job shifts from building a PC to advancing one. Unlike a physical computer, where the CPU, PIC, PIT, DMA, video, sound, and input devices all run concurrently, DOSBox-X drives all of them from a single execution loop. The loop has to reproduce that concurrency itself — placing each device event at the correct point on the same virtual timeline — regardless of host performance or the configured CPU speed.

The question this chapter answers is therefore a precise one: **how does DOSBox-X know exactly when to stop executing the CPU so that a scheduled event can occur?** The answer is not where you would first look for it — not in the CPU core, which merely runs instructions, and not in `main()`, which only starts the loop rather than deciding anything. The decision lives in `pic.cpp`, a file named for the interrupt controller and giving no hint that it also gates the CPU. Following the path from `main()` — through `DOSBOX_RunMachine()` and `Normal_Loop()` — the trail ends there, in `PIC_RunQueue()`.

A note on what "the scheduler" means here: `PIC_RunQueue()` and the machinery around it do not implement device behavior. They compute a due/not-due answer and a cycle count, and dispatch an event to its handler when one comes due; what that handler actually does is up to the device code on the other side of the call. The scheduler's entire job is deciding *when* control passes to each of them.

Before going further, here is the mental model this chapter keeps returning to:

<Diagram src="04-scheduling-loop.svg" />

The queue holds *what* is due and *when*; the scheduler converts the next deadline into a cycle budget; the CPU merely executes within that budget and returns. By §4.9 this picture gains a feedback arrow, because the queue can reach back and rewrite the CPU's budget while a batch is still in flight. To answer the chapter's opening question, the path runs from `main()` to the scheduler, then through how events are enqueued and dispatched, and finally to how the CPU budget is computed from the next deadline.

## 4.2 From `main()` to `Normal_Loop()` {#from-main-to-normal-loop}

A first surprise: `main()` lives in `src/gui/sdlmain.cpp` — the entry point sits in the SDL frontend file even though most of what it sets up belongs to the CPU/device emulator, a naming artifact inherited from DOSBox's original single-frontend design. Startup proceeds:

1. Parse command line arguments (`DOSBOX_parse_argv`)
2. Bring up early logging (`LOG::EarlyInit`)
3. Build the `Config` object and register config sections for every subsystem — CPU, VGA, sound cards, serial, DOS kernel — each gets a chance to register its `.conf` keys before anything is instantiated
4. Call `DOSBOX_RunMachine()`

That call is the boundary. Nothing before it involves the CPU or a single emulated device; everything after it, for the rest of this chapter and most of this book, does.

```cpp
// src/dosbox.cpp — trimmed to the control-flow skeleton; the real function
// also saves and restores a `last_callback` bookkeeping variable around
// the loop, which matters for nested calls (§4.12) but not for this pass
void DOSBOX_RunMachine(void){
    Bitu ret;
    do {
        ret = (*loop)();
    } while (!ret);
}
```

At first glance, `DOSBOX_RunMachine()` appears to be little more than a wrapper around the CPU — and, bafflingly, that impression is *almost* the whole truth. It repeatedly invokes a function pointer named `loop` until the handler returns non-zero, and that is the entire body (see the skeleton just above). The next few paragraphs explain why something so small is nevertheless where the machine actually runs.

If `loop` is just a function pointer, two questions follow immediately: what installs it, and does anything else ever take it over mid-run?

```cpp
typedef Bitu (LoopHandler)(void);
static LoopHandler* loop;
```

`DOSBOX_SetLoop()` (`src/dosbox.cpp`) is the only way to install a non-`Normal_Loop` handler; a sibling, `DOSBOX_SetNormalLoop()`, just sets it back to `Normal_Loop` (the debugger uses it to restore the loop after pausing). It is called once at startup:

```cpp
DOSBOX_SetLoop(&Normal_Loop);
```

After that startup installation, the only subsystem that ever replaces the loop is the interactive debugger (`DEBUG_Loop`), and only while it is paused — single-stepping or stopped at a breakpoint. The moment the machine is actually running, the debugger forwards straight back to `Normal_Loop`. No other subsystem swaps the loop handler; rebooting uses exception unwinding, not loop replacement, a point taken up in §4.12.

The path this section has traced is short enough to hold in one line, and it's the path everything else in this chapter hangs off of:

```text
main()
  ↓
DOSBOX_RunMachine()
  ↓
loop()
  ↓
Normal_Loop()
```

## 4.3 `Normal_Loop` {#normal-loop}


So what does `Normal_Loop` actually do? Before the loop body, it refreshes the window title's cycle-rate readout (and, if tick reporting is enabled, logs a tick report), then enters its `try { while (1) }` body. The prologue at the top of `Normal_Loop()` in `src/dosbox.cpp` is:

```cpp
// src/dosbox.cpp — Normal_Loop(), prologue before the try/while body
if (!menu.hidecycles || menu.showrt) {
    uint32_t ticksNew = GetTicks();
    if (ticksNew >= Ticks) {
        ...                                       // recompute frames / interval
        GFX_SetTitle((int32_t)CPU_CycleMax, -1, -1, false);  // refresh cycle-rate readout
        frames = 0;
    }
}
if (control->opt_print_ticks)
    LOG_MSG("Tick report: SDL=%lu emu=%.6f", ...);          // optional tick-rate log
```

The loop body itself — slightly condensed — is:

```cpp
try {
    while (1) {
        if (PIC_RunQueue()) {
            CPU_Check_NMI();
            ret = (*cpudecoder)();
            if (ret < 0) return 1;
            if (ret > 0) {
                // dispatch to CallBack_Handlers[ret]
                ...
            }
        } else {
            GFX_Events();
            if (!DOSBox_Paused() && ticksRemain > 0) {
                TIMER_AddTick();
                ticksRemain--;
            } else {
                increaseticks();
                return 0;
            }
        }
    }
} catch (int x) {
    // exceptional control flow
}
```

One call decides which branch runs on every pass through this loop: `PIC_RunQueue()`. It returns `true` when it has established a positive CPU execution budget, `false` when no CPU cycles remain to be executed before the next millisecond-level pacing step.

**When it returns `true`** — the CPU path — `(*cpudecoder)()` runs one batch of instructions (the interpreter or dynamic core, covered in @chapter(interpreter-core, short)–@chapter(dynamic-recompilation, short)). A negative return stops `Normal_Loop` outright. A positive return is a callback ID: the decoder hit an interrupt stub or I/O trap that needs C++ code instead of guest instructions, and `Normal_Loop` dispatches to `CallBack_Handlers[ret]`.

**When it returns `false`** — the time/pacing path — the CPU has used its cycle budget for this millisecond. `GFX_Events()` pumps host input and window events, `TIMER_AddTick()` advances the millisecond clock if any ticks remain, and otherwise `increaseticks()` runs and `Normal_Loop` returns to `DOSBOX_RunMachine`, which immediately calls it again.

Neither branch is optional and neither runs without asking `PIC_RunQueue()` first. Whatever that function decides, it determines the execution budget for every CPU burst the guest executes.

`Normal_Loop()` does not schedule events at all. It never inspects the event queue, never computes a deadline, never decides when the CPU should stop. It merely asks `PIC_RunQueue()` a single yes/no question — *may the CPU run now?* — and obeys the answer. The loop that you might have assumed was *driving* the machine is in fact just a courier between the scheduler and the decoder. §4.3 established what the courier does; §4.4 examines the scheduler it queries.

## 4.4 `PIC_RunQueue` {#pic-runqueue}


Here's the question that matters: how does DOSBox-X stop the CPU from running straight past the next VGA retrace, PIT tick, or DMA completion? Nothing in `Normal_Loop` polls for those events directly — it just asks `PIC_RunQueue()` a yes/no question. The answer has to be coming from somewhere.

`PIC_RunQueue` (`src/hardware/pic.cpp` — the same file that owns the event queue this whole chapter revolves around, alongside the emulated 8259 covered in @chapter(interrupts-exceptions-pic)) reads, going in, like an interrupt-controller helper — the file also contains the emulated 8259 (`PIC_Controller`, IRQ masking, cascade logic), and "PIC" is the 8259's name. By the end of this function that reading turns out to be incomplete.

It does three things, in order, on every call that finds cycles remaining in the current millisecond — and read together they tell a single story: **recover → dispatch → allocate.**

**1. Recover — roll unspent cycles forward.**

```cpp
// src/hardware/pic.cpp, top of PIC_RunQueue()
CPU_CycleLeft += CPU_Cycles;
CPU_Cycles = 0;
```

**Why would the scheduler need to take cycles back?** Because the previous batch may have ended early — a callback, a guest exception, a mode change — leaving work unspent. Rather than discard it, `PIC_RunQueue()` folds whatever remains in `CPU_Cycles` back into `CPU_CycleLeft`. Everything below this operates on `CPU_CycleLeft`, never on the previous `CPU_Cycles`. This is the *recover* step: consolidate whatever the last burst left behind before deciding what comes next.

**2. Dispatches expired events.**

This step turns on a distinction the rest of the chapter depends on: **enqueuing** puts an entry into `pic_queue` (the subject of §4.6), while **dispatching** — what this step actually does — pulls a due entry out and calls its handler. Four terms ride on that distinction, and the chapter uses them consistently from here on: an event's **deadline** is the scheduled time it was enqueued with; the event is **due** once the current execution position — `PIC_TickIndexND()`, measured in cycle-equivalent units — has reached it, where "reached" also covers the few cycles a translated block can overshoot by, or a deadline enqueued after the position had already advanced; its **handler** is the device-side function called when it becomes due. Hold onto one fact: dispatching happens only here, in this single loop, and only for entries whose deadline has actually arrived — never from inside a handler that happens to be running. Treating enqueuing and dispatching as the same moment (scheduling an event and running it as one act) is the surest way to misread what follows.

```cpp
while (pic_queue.next_entry &&
       (pic_queue.next_entry->index * CPU_CycleMax <= index_nd)) {
    PICEntry * entry = pic_queue.next_entry;
    pic_queue.next_entry = entry->next;
    (entry->pic_event)(entry->value);
    // return entry to free list
}
```

`index_nd` — which is `PIC_TickIndexND()` (see @section(time-in-dosbox-x/turning-work-into-simulated-time, short), Chapter 3 §3.8; the undivided numerator of `PIC_TickIndex()`) — is how far into the current millisecond execution has progressed, in cycle-equivalent units. `pic_queue` holds every device event currently scheduled: a VGA retrace, a DMA completion, a sound card IRQ, a serial byte. Each carries a fractional-tick `index`, and the queue stays sorted by that index (§4.6), so checking only the head is enough to know whether anything is due. Firing an entry calls its handler directly, synchronously — the handler runs to completion before `PIC_RunQueue` does anything else.

`index_nd` is intentionally left in cycle units rather than fractional ticks so that it can be compared directly against `pic_queue.next_entry->index * CPU_CycleMax`, avoiding an unnecessary division during the scheduler's hot path. §4.7 makes that conversion — and the two unit systems it bridges — explicit.

**In other words:** the instant a deadline is reached, the scheduler stops being a budget-calculator and becomes an executor — it runs device code *before* it ever hands the CPU another slice. That ordering, *service the event first, then decide how much CPU may run*, is the entire reason the CPU can never overrun a deadline. This is the *dispatch* step.

One related detail this chapter sets aside: `PIC_RunQueue()` also delivers any pending 8259 interrupts via `PIC_runIRQs()` at this same point (whenever `PIC_IRQCheck` is set) — both before the event-dispatch loop and again after the budget is allocated (`src/hardware/pic.cpp`). That path belongs with the PIC itself in @chapter(interrupts-exceptions-pic); the point that matters here is merely that interrupt delivery happens *inside the same function* that sizes the CPU budget, so it too is bounded by the scheduler rather than running on the CPU's own initiative.

**3. Allocate — compute the next cycle budget.**

```cpp
if (pic_queue.next_entry) {
    Bits cycles = (Bits)(pic_queue.next_entry->index * CPU_CycleMax - index_nd);
    if (!cycles) cycles = 1;   // never hand the decoder a zero-cycle batch
    CPU_Cycles = (cycles < CPU_CycleLeft) ? cycles : CPU_CycleLeft;
} else {
    CPU_Cycles = CPU_CycleLeft;
}
CPU_CycleLeft -= CPU_Cycles;
```

If another event is pending, the CPU gets exactly enough cycles to reach it, no more. If the queue is empty, it gets whatever remains of the millisecond's budget. The final `CPU_CycleLeft -= CPU_Cycles` is arranged so that the unallocated portion of the current millisecond's budget stays in `CPU_CycleLeft` while the just-allocated portion moves into `CPU_Cycles` — together they still account for the same total this function started with, which is the quantity `PIC_TickIndexND()` measures against `CPU_CycleMax` in §4.7. Either way, the number handed to `(*cpudecoder)()` back in `Normal_Loop` was never the CPU's to choose.

The return value is just "is there still a positive cycle budget?" — the yes/no `Normal_Loop` asked for.

This is the *allocate* step, and with it the **recover → dispatch → allocate** story is complete: consolidate leftovers, fire anything now due, then hand the CPU exactly enough cycles to reach the next deadline and no more.

Reread the filename. `PIC_RunQueue` lives in `pic.cpp`, the same file that owns the emulated 8259 interrupt controller, and "PIC" *is* the 8259's name — so on the way in it reads like an interrupt-controller helper. The file's name undersold it. `PIC_RunQueue` is not an interrupt-controller helper that happens to also gate the CPU; **gating the CPU is the job.** A function named for the interrupt controller turns out to be the single place in the emulator that decides how much the processor gets to run.

That settles the mystery from §4.1, but it raises a cleaner question for the rest of the chapter: what does `PIC_RunQueue()` deliberately *not* do, and what other code fills those gaps? §4.5–§4.11 follow those gaps — and §4.13 will state the rule this whole function exists to enforce.

## 4.5 CPU Execution Is a Consumer of the Budget {#cpu-execution-is-a-consumer-of-the-budget}


The relationship §4.4 established is the foundation for every CPU chapter that follows: `PIC_RunQueue()` does not execute the CPU. It authorizes execution, in whole-cycle units, and then gets out of the way:

```
PIC_RunQueue()
       │
       │  sets CPU_Cycles = N
       ▼
  (*cpudecoder)()
       │
       │  consumes up to N cycles,
       │  then returns
       ▼
  Normal_Loop()
       │
       │  loops back around
       ▼
PIC_RunQueue()
```

`(*cpudecoder)()` — the interpreter or the dynamic core, covered starting in @chapter(interpreter-core, short) — never asks *how much* it's allowed to run. It reads `CPU_Cycles`, counts down against it one instruction (or, in the dynamic core, one translated block) at a time, and stops when the count reaches zero or a callback interrupts it early. It has no way to request more, and it does not participate in deciding why that budget has the value it does; that decision belongs to the scheduler. That's deliberate: the decoder's job is entirely local — decode, execute, update guest state — and the scheduler's job is entirely about *when*. Neither needs to know how the other one works.

A qualification belongs here, before the model feels too clean: "the CPU runs until the next scheduled event" describes the *normal* path, not the *only* path. A CPU burst can also end early because of a guest exception, a debugger breakpoint, a callback (an `INT`-style trap into C++ code), a mode change (real mode to protected mode and back) — which in the dynamic core invalidates the translated code and, under `cycles=auto`, explicitly zeroes the cycle budget — or — for the dynamic recompiler covered in @chapter(dynamic-recompilation, short) — a core switch. All of these are uncommon relative to ordinary scheduled-event boundaries, and none of them change the architecture this chapter describes; they're simply additional reasons a batch can be shorter than its nominal cycle budget. They'll each get their own treatment in the chapters where they're actually relevant.

One case worth separating out explicitly, because it looks like an early terminator but isn't: a hardware IRQ does not cut a running burst short. An IRQ only becomes *pending* — a device raises it and sets `PIC_IRQCheck` — and it is *delivered* only when `PIC_RunQueue()` next runs `PIC_runIRQs()` at the start of its recover step, before `(*cpudecoder)()` is ever called. So a hardware interrupt opens the *next* burst (the ISR runs as that burst's work) rather than ending the current one. A software `INT nn`, by contrast, *is* an early terminator — but it is exactly the callback case above: the decoder returns the interrupt's callback ID, and `Normal_Loop` hands control to `CallBack_Handlers[ret]`. This is the force of §4.4's note that IRQ delivery lives inside `PIC_RunQueue()` and is therefore bounded by the same scheduler that sizes the budget.

That gating has a cost that isn't fixed. `PIC_RunQueue` itself runs in roughly constant time — an O(1) budget recompute plus however many entries happen to be due, usually zero or a handful. What it hands off varies enormously: the CPU path that follows can consume anywhere from a handful of cycles' worth of host time to nearly a full millisecond, depending on the configured `cycles=` value and host speed, while the time/pacing path costs microseconds unless `increaseticks()` reaches an actual sleep (§4.11). The function's own cost never changes; what it authorizes does.

This matters beyond the mechanics of the loop itself. @chapter(interpreter-core, short) and @chapter(dynamic-recompilation, short) cover the CPU core — the interpreter and the dynamic recompiler that decode and execute x86 instructions — and both build on a premise this chapter establishes: that the CPU never runs on its own terms. It is invoked, handed a specific number of cycles, and stopped, by something else. That something else is what this chapter traces. Once it's clear what decides how much the CPU gets to run and when, the CPU chapters that follow are chapters about a component that takes orders, not one that drives the machine.

## 4.6 Event Scheduling {#event-scheduling}


*A quick position check before this section: we're stepping one level sideways from the `main()` → `DOSBOX_RunMachine()` → `Normal_Loop()` → `PIC_RunQueue()` path, not moving further down it. `PIC_RunQueue()`, just covered, only dispatches what's already sitting in `pic_queue`. Before returning to that path, it's worth seeing where those entries get enqueued in the first place.*

`PIC_RunQueue` only dispatches what's already in `pic_queue`. Where do those entries come from?

```cpp
// src/hardware/pic.cpp — omits the free-list-exhausted guard at the top
// (a LOG_MSG + early return if pic_queue.free_entry is NULL), which
// doesn't bear on how a successful enqueue works
void PIC_AddEvent(PIC_EventHandler handler, pic_tickindex_t delay, Bitu val) {
    PICEntry * entry = pic_queue.free_entry;
    if (InEventService) entry->index = delay + srv_lag;
    else entry->index = delay + PIC_TickIndex();
    entry->pic_event = handler;
    entry->value = val;
    pic_queue.free_entry = pic_queue.free_entry->next;
    AddEntry(entry);   // insertion-sorted into the queue by index
}
```

Calling `PIC_AddEvent()` *schedules* an event but does not *run* it. The handler you pass in is merely stored; it will execute later, inside `PIC_RunQueue()`'s dispatch step (§4.4), at the deadline you gave it — not now, and not on the calling thread's timeline. This is the distinction the §4.4 vocabulary was protecting: **enqueuing is not dispatching.** A PIT handler that re-arms itself, for example, has not "run the next event"; it has only placed another deadline into the queue while the current handler is still on the stack.

The entry pool is a fixed-size free list (`PICEntry entries[PIC_QUEUESIZE]`), not a dynamic allocation. Because the event pool is fixed-size, successful calls to `PIC_AddEvent()` do not perform dynamic allocation. This removes allocator activity from the event-enqueue path. `AddEntry` inserts the new entry in sorted position by `index`, which is exactly what let `PIC_RunQueue` get away with checking only the head of the queue in §4.4. If the free list is exhausted, `PIC_AddEvent()` logs an error and returns without enqueuing — a device that can't get a slot simply loses its event rather than corrupting the pool.

What if two events have exactly the same deadline? `AddEntry` walks the list looking for the first existing entry whose index is *strictly greater* than the one being inserted, and stops there — which means a tie is never displaced. A new entry with the same `index` as entries already in the queue is inserted after all of them, not before, not at an arbitrary position. Ties therefore resolve in arrival (insertion) order, deterministically: when two events share the same deadline, the one enqueued first sits nearer the head and is dispatched first. That gives simultaneously due events a defined ordering — first-arrived, first-dispatched — rather than leaving their relative order dependent on list traversal or host scheduling.

Periodic events are anchored to their scheduled deadline, not to the time at which their handler happens to finish. That is what the `InEventService`/`srv_lag` branch is for: when a handler currently being dispatched by step 2 of `PIC_RunQueue` calls `PIC_AddEvent` again — as periodic events, a PIT channel rearming itself, routinely do — the new entry is scheduled relative to `srv_lag`, the index of the event being serviced, not relative to wherever the CPU happens to be right now. Without that anchoring, a re-arming timer would drift a little further behind on every tick as handler execution time accumulated into its scheduling delay; with it, that execution time is not counted as additional delay.

Every hardware subsystem introduced later in this book eventually reaches this function. VGA schedules retrace events here. The PIT schedules timer expirations here. DMA schedules transfer completion here. The details differ by device; all of them join the same queue before control ever returns to the CPU.

## 4.7 From Event Deadline to CPU Budget {#from-event-deadline-to-cpu-budget}

The CPU speaks in cycles; the event queue speaks in fractional milliseconds. One number has to stop the other, but they don't share a unit. How can a deadline expressed in milliseconds ever tell an instruction stream how many cycles it may run?

The bridge between the two systems is a single value: **`CPU_CycleMax`**, declared and defined in @section(time-in-dosbox-x/the-cycle-budget-how-guest-work-is-measured, short) (Chapter 3 §3.7). It defines the nominal CPU-cycle budget assigned to one simulated millisecond — not a promise that exactly that many cycles will execute. When the user changes `cycles=` (or the automatic cycle controller adjusts it — @chapter(timing-and-cycle-management)), this value changes, but the scheduler's notion of elapsed time does not.

Chapter 3 already derived the two helpers this bridge rests on: `PIC_TickIndex()` (cycles consumed → millisecond fraction) and its inverse `PIC_MakeCycles()` (a fractional-millisecond delay → cycle count), both in @section(time-in-dosbox-x/turning-work-into-simulated-time, short) (Chapter 3 §3.8). The key reuse here is that `pic_queue.next_entry->index * CPU_CycleMax` in §4.4 is exactly `PIC_MakeCycles(next_entry->index)`, written inline. What §4.7 adds is the hot-path form: `PIC_RunQueue()` compares a queue entry's deadline against cycles already consumed many times per millisecond, and doing that in cycle units avoids a floating-point divide on every check. `PIC_TickIndexND()` — the undivided numerator of `PIC_TickIndex()`, `CPU_CycleMax - CPU_CycleLeft - CPU_Cycles` — supplies exactly that, left in cycle units instead of a 0.0–1.0 fraction. That is the form `index_nd` needs.

For example, the Sound Blaster DSP reset (see @section(sound/the-dsp-commands-not-a-direct-line-to-audio, short)) schedules a 20 μs delay. With `CPU_CycleMax = 3000`, that is `0.02 ms × 3000 = 60 cycles`; doubling `CPU_CycleMax` makes the same 20 μs become 120 cycles. The device timing has not changed — only the amount of CPU work that now fits into the same simulated interval.

## 4.8 Event-Bounded CPU Execution {#event-bounded-cpu-execution}

Put §4.4's three steps and §4.7's conversion together and the CPU's instructions make a claim worth stating plainly, because it's easy to read past it: the CPU is never handed an unconditional "run for one millisecond." It's handed "run until the next queued event's deadline, or until this millisecond's budget runs out — whichever comes first." When the queue is empty, only the second clause is in force, so the CPU does receive the full millisecond's worth of cycles (the whole `CPU_CycleLeft`); the claim is only that the duration is always derived from the queue or the budget, never fixed in advance.

```text
next queued event's deadline
       │
       │  − cycles already consumed this millisecond (§4.7's index_nd)
       ▼
   cycle distance to that deadline
       │
       │  clamped against whatever's left of CPU_CycleLeft
       ▼
       CPU_Cycles
       │
       ▼
   (*cpudecoder)()
```

What if the queue were empty — nothing waiting at all? Then there is no deadline to protect, and the scheduler stops pretending there is one: `CPU_Cycles` becomes simply whatever remains of `CPU_CycleLeft`, the entire leftover budget for this millisecond (the ordinary case §4.4's step 3 already showed). If an event is pending instead, the batch is sized to reach the event deadline without intentionally allocating cycles beyond it.

Why schedule events to sub-millisecond, fractional precision at all, rather than rounding everything to the nearest whole millisecond — that 20 μs Sound Blaster delay from §4.7 is, after all, two hundredths of a millisecond? If `PICEntry.index` had only millisecond granularity, every event due inside the same millisecond would collapse onto the same deadline; §4.6's insertion-order tie-break would still give them a defined dispatch order, but the queue would have lost the information that, say, a DMA completion actually belonged 60 cycles into the millisecond while a VGA retrace belonged 1,400 cycles in. Fractional-millisecond scheduling is what preserves that relative positioning: a DMA completion can be scheduled at one position within the millisecond while a VGA retrace or timer event is scheduled at another, and the scheduler carries those positions through into CPU-cycle units rather than collapsing them. `CPU_CycleMax` provides the mapping that lets those fractional-millisecond deadlines be enforced in the CPU's integer cycle accounting.

So far this covers the common case: a batch is sized against the queue as it stands, and the CPU runs until the budget is exhausted or the deadline is reached. One case remains — what if an event is scheduled *while* a batch is already running?

## 4.9 When a New Event Shrinks an Existing Batch {#when-a-new-event-shrinks-an-existing-batch}


What if a new event appears after the CPU has already started its batch? §4.4 described `PIC_RunQueue()` computing a batch once, at the top of a pass through `Normal_Loop`'s `while(1)`, and handing it to the decoder. That's the common case — but it leaves the picture slightly too clean. Cycle exhaustion isn't only something the CPU discovers for itself by counting down to zero. `AddEntry` — the same insertion routine §4.6 just covered — can reach back and shrink a batch that's already in flight, before the decoder has even had a chance to notice. Recall the model from §4.1: the queue was drawn as a one-way arrow into the scheduler, but here the queue reaches *back* into a batch already running.

Enqueuing an event can invalidate an already-issued CPU budget: the batch was sized against the queue as it stood a moment ago, but a newer, sooner deadline quietly makes that sizing wrong on the spot. After inserting the new entry in sorted order, `AddEntry` checks whether it's now sooner than whatever deadline the CPU's current batch was sized against, and if so, zeroes out `CPU_Cycles` right then, on the spot:

```cpp
// src/hardware/pic.cpp, end of AddEntry()
Bits cycles = PIC_MakeCycles(pic_queue.next_entry->index - PIC_TickIndex());
if (cycles < CPU_Cycles) {
    CPU_CycleLeft += CPU_Cycles;
    CPU_Cycles = 0;
}
```

This is what happens when a guest instruction *itself* schedules an event sooner than the batch it's currently running in — an `OUT` to a Sound Blaster DSP port that arms a DMA-completion event, say:

```
CPU mid-batch, CPU_Cycles = 1000 remaining
       │
       │  guest OUT instruction calls PIC_AddEvent()
       ▼
   AddEntry() inserts the new, sooner deadline
       │
       │  new deadline < current batch's deadline
       ▼
   CPU_Cycles zeroed on the spot
       │
       ▼
   decoder's countdown hits zero on its very next check
       │
       ▼
   control returns to Normal_Loop() → PIC_RunQueue()
       │
       ▼
   a new, correctly shorter budget is computed
```

Nothing about the decoder itself changes — it's still just counting `CPU_Cycles` down to zero the way §4.5 described. What changes is *how quickly* it gets there: the countdown that was sized against a now-stale deadline gets cut short by an enqueue that happened in the middle of the batch it's cutting short. So "`CPU_Cycles` reaches zero, then the scheduler runs" is the common case, but not the only trigger — a freshly enqueued event can invalidate the remaining, not-yet-consumed portion of an allocation that's already in flight, which is enqueuing reaching back to affect dispatch timing before the queue is ever checked again.

This is also the check that protects the scheduler's central guarantee: the CPU must never execute past the next event's deadline. The batch was sized against the queue as it stood when `PIC_RunQueue()` last ran; without this zeroing, the CPU could keep running straight through a deadline that only appeared afterward, because nothing re-checks the queue until `PIC_RunQueue()` is called again. By invalidating the in-flight budget the instant a sooner event is enqueued, `AddEntry` closes that gap — so even a deadline that arrives mid-batch is honored. (§4.13 states this guarantee as an explicit contract.)

## 4.10 Completing a Millisecond {#completing-a-millisecond}


*Back on the main path now: this is the host branch of `Normal_Loop()`'s `while(1)` — the one that runs when §4.4's `PIC_RunQueue()` reports the budget exhausted, not the CPU branch.*

Not everything a device needs to do belongs on that queue — and that's a separate mechanism from anything §4.4 or §4.6 covered.

When `PIC_RunQueue()` reports the budget exhausted, `Normal_Loop`'s host path calls `TIMER_AddTick()` (`src/hardware/pic.cpp` — the `TIMER_` prefix is a naming holdover from DOSBox's original split between "PIC" and "TIMER" concepts, never fully separated). `TIMER_AddTick()` advances the guest millisecond clock (`PIC_Ticks++`), refills the cycle budget (`CPU_CycleLeft += CPU_CycleMax + CPU_Cycles`), ages event deadlines (`entry->index -= 1.0`), and runs registered tick handlers. See @section(time-in-dosbox-x/the-cycle-budget-how-guest-work-is-measured, short) (Chapter 3 §3.7) and @section(time-in-dosbox-x/keeping-the-simulation-synchronized, short) (Chapter 3 §3.9) for the complete lifecycle and code.

`CPU_CycleMax` sizes the per-millisecond refill, but it does not set event timing — the events themselves are aged by exactly one millisecond regardless of how large the refill is. That separation is what lets `cycles=` change how much CPU work fits in a millisecond without changing when scheduled events fire.

Once `TIMER_AddTick()` returns, the cycle accounting has been replenished for the newly elapsed millisecond, so the next call to `PIC_RunQueue()` back in `Normal_Loop`'s `while(1)` can establish a new CPU budget. The loop is back in the CPU path.

Seen together, `PIC_RunQueue()` and `TIMER_AddTick()` divide the scheduler into two complementary responsibilities. `TIMER_AddTick()` advances simulated time by exactly one millisecond and ages every pending event by that same amount. `PIC_RunQueue()` never advances time itself; instead, it repeatedly converts the queue head's millisecond deadline into a cycle budget using `CPU_CycleMax`, allowing the CPU to execute only until the next event becomes due. Raising `cycles=` therefore never makes timers fire earlier — it simply increases how much CPU work fits inside each simulated millisecond before the scheduler must stop and service the next event.

## 4.11 Returning to Host-Time Pacing {#returning-to-host-time-pacing}

*Still on the main path, still inside `Normal_Loop()`'s host branch — one level further in, at the `ticksRemain` check §4.10 just used but didn't yet explain.*

One question is still open: what decides that another simulated millisecond is owed, and when? Contrary to what its name suggests — `TIMER_AddTick()` advances the simulated clock — it is *not* triggered by any periodic timer callback of its own. It only ever fires from the host branch of `Normal_Loop` that §4.2 already introduced. The three timing domains this rests on — host wall-clock time, guest completed milliseconds, and CPU cycle accounting — are introduced in @section(time-in-dosbox-x/three-timing-domains, short) (Chapter 3 §3.4).

```cpp
} else {
    GFX_Events();
    if (DOSBox_Paused() == false && ticksRemain > 0) {
        TIMER_AddTick();
        ticksRemain--;
    } else {
        increaseticks();
        return 0;
    }
}
```

`ticksRemain > 0` is the actual gate, and §3.9 already covers what fills it: `increaseticks()` (`src/dosbox.cpp`) samples real elapsed wall-clock time via `GetTicks()` and converts it into a count of guest milliseconds that have become due. This chapter only needs the control-flow consequence of that: as long as `ticksRemain` is positive, `Normal_Loop`'s host branch drains it one `TIMER_AddTick()` at a time, decrementing on each call, before ever asking `increaseticks()` to sample the host clock again. Once the backlog reaches zero, `increaseticks()` runs, and — per §3.9's catch-up mechanism — either hands back a fresh `ticksRemain` or, if no host time has actually elapsed yet, sleeps briefly and returns without touching it at all, leaving the `while(1)` loop to simply ask again next pass.

`TIMER_AddTick()`, in other words, is paced by real elapsed host time, not by an internal periodic callback of its own — under normal pacing, `PIC_Ticks` advances because `increaseticks()` determines that additional guest milliseconds are owed from elapsed host time. That's also what fully answers §4.7: `increaseticks()` decides *when* a new simulated millisecond begins; `CPU_CycleMax` decides how much CPU work is allowed to happen inside it once it has.

Turbo mode — `ticksLocked`, set from the `turbo` config key — is the one place this chapter needs to name the exception rather than just cross-reference it, because it changes what "the gate" in the code above actually does: it skips `increaseticks()`'s real-time check entirely and hands `Normal_Loop` a fixed `ticksRemain = 5` on every pass, regardless of whether any host time has elapsed. `TIMER_AddTick()` itself doesn't change at all — same call, same simulated millisecond, same `CPU_CycleMax`-sized refill — only the pacing gate in front of it is removed. §3.10 covers why that trade-off exists and what it costs; this chapter's business with it ends at "the gate normally paces `TIMER_AddTick()` against the wall clock, and Turbo removes the gate."

## 4.12 Exceptional Control Flow {#exceptional-control-flow}


*This one's a detour: it closes two loose threads (§4.2's rebooting assumption, §4.3's positive-return case) rather than going one level deeper. §4.13 returns to the main path.*

§4.2 left an assumption open: if `LoopHandler` can be swapped, rebooting ought to install a different one. It never does. `DOSBOX_SetLoop()` has exactly two callers, `Normal_Loop` and `DEBUG_Loop`, and neither has anything to do with rebooting. Rebooting and shutdown don't swap loop handlers — they unwind the stack instead. Emulated hardware or host events throw integer exceptions caught at the top level in `main()`, which set state flags (`run_machine`, `reboot_machine`, `dos_kernel_shutdown`) and re-enter `DOSBOX_RunMachine()`. Callbacks like `CALLBACK_RunRealFar` use recursive `DOSBOX_RunMachine()` calls with a `stop_handler` to return control. The detailed exception values and their meanings are covered just below, in the Appendix: Exception-Based Reboot Mechanism.

## Appendix: Exception-Based Reboot Mechanism

This appendix holds the detailed throw/catch mechanics summarised in §4.12.

### Positive-return callbacks and recursive re-entry

A callback returning a positive value from inside the CPU path is not "the whole emulator must stop." Helpers like `CALLBACK_RunRealFar`, `CALLBACK_RunRealFarInt`, and `CALLBACK_Idle` in `src/cpu/callback.cpp` need to run a piece of real-mode guest code to completion and then regain control — they do it by calling `DOSBOX_RunMachine()` recursively:

```cpp
// src/cpu/callback.cpp — one of several call sites
DOSBOX_RunMachine();
```

Before the call, the helper pushes a fake return address pointing at a `stop_handler` callback. When the guest code returns, execution lands there, `stop_handler` fires, and returns:

```cpp
// include/callback.h
enum {
    CBRET_NONE=0, CBRET_STOP=1
};
```

`Normal_Loop` propagates `CBRET_STOP` straight out, stopping the *nested* `do/while` in that recursive `DOSBOX_RunMachine()` call — control returns to whichever `callback.cpp` helper started it, not to the outermost frontend. `DOSBOX_RunMachine` is declared `void`; the value never travels past the `do/while` immediately around it. A non-zero callback return means "this nested call is done," not "stop the emulator."

### Top-level catch and exception values

Actual shutdown and reboot bypass `loop` entirely. `Normal_Loop`'s body is wrapped in `try`, with two typed catches before the one this section cares about — `GuestPageFaultException` and `GuestGenFaultException`, which convert a host-side C++ exception back into a guest CPU exception and belong with @chapter(memory-model-and-address-translation)'s page-fault handling, not here. The `catch (int x)` that follows absorbs exactly one case:

```cpp
// src/dosbox.cpp, inside Normal_Loop's try/catch
catch (int x) {
    dosbox_allow_nonrecursive_page_fault = saved_allow;
    if (x == 4 /* CMOS shutdown */) {
        ret = 0;
    } else {
        throw;   // everything else propagates upward, unhandled here
    }
}
```

Every other value is rethrown, unwinding through `DOSBOX_RunMachine`'s `do/while` — which has no `try`/`catch` of its own — up to the outermost call site in `main()` (`src/gui/sdlmain.cpp`), which dispatches on the exact integer:

```cpp
// src/gui/sdlmain.cpp, around the top-level DOSBOX_RunMachine() call
try {
    DOSBOX_RunMachine();
} catch (int x) {
    if (x == 2) {
        // booting a guest OS; image already loaded, CPU registers already set up
        run_machine = true;
        dos_kernel_shutdown = !dos_kernel_disabled;
    } else if (x == 3) {
        // reboot the whole system
        reboot_machine = true;
        dos_kernel_shutdown = !dos_kernel_disabled;
    } else if (x == 6) {
        // reboot the DOS kernel only
        reboot_dos = true;
        dos_kernel_shutdown = !dos_kernel_disabled;
    }
    // ...several more cases follow the same shape: set a state flag,
    // let dos_kernel_shutdown mirror dos_kernel_disabled, fall through —
    // booting into a BIOS image, restarting a corrupted DOS kernel, and
    // a couple of narrower legacy signals
    else {
        // kill switch — see throw(0) / throw(1) call sites elsewhere in the tree
        run_machine = false;
        dos_kernel_shutdown = false;
    }
}
```

### Throw sites

The `throw` sites are wherever emulated hardware or host-event code needs to force a transition: `CheckQuit()` in `sdlmain.cpp` (`throw(0)` on window-close/quit-confirmed), BIOS POST/reboot handling in `src/ints/bios.cpp` (`throw 1` for shutdown-and-exit), and similar sites elsewhere. None of them touch `loop`. A reboot is: unwind the stack to `main()`'s `try`, set the appropriate state flags, call `DOSBOX_RunMachine()` again — the same `Normal_Loop` throughout. The source's own comment near one throw site calls the mechanism "a stupid and nondescriptive way to signal shutdown/reset."

## 4.13 The Scheduler as a Contract {#the-scheduler-as-a-contract}


Everything from §4.3 through §4.12 has been procedural — this function does this, that field means that. Now that all the pieces are on the table, the single rule that all of it exists to enforce is worth stating directly:

> **The scheduler must not intentionally allow CPU execution to advance beyond the deadline of the next scheduled event.**

This is the scheduling invariant the cycle-budget mechanism is designed to enforce. It sounds almost too simple to be load-bearing, but nearly everything this chapter has traced falls directly out of it:

- **Why cycle budgeting exists at all** (§4.4): the CPU can't be handed an open-ended "run until told to stop," because there's no way to guarantee it would stop exactly at the next event's deadline rather than overshooting it. A bounded batch sized to the next deadline gives the scheduler a direct mechanical way to enforce the contract rather than relying on the CPU to check often enough.
- **Why the queue stays sorted by `index`** (§4.6): the contract is about the *next* event specifically — the soonest deadline — so the only entry that ever matters for sizing a batch is the head of the queue. An unsorted queue would mean scanning every entry, every batch, to find out which one the contract currently applies to.
- **Why `AddEntry` can retroactively shrink an in-flight batch** (§4.9): a batch computed against the queue as it stood a moment ago can be invalidated by a newly enqueued event that's now sooner. The contract doesn't say "honor the deadline you knew about when the batch started" — it says the scheduler must not *intentionally* let execution advance past the next event's deadline, so a newer, closer deadline has to win even mid-batch.
- **Why execution happens in bounded slices instead of one continuous run** (§4.1, §4.4): a slice is bounded by exactly one thing — the next deadline the contract is currently protecting. Once that deadline is reached, the contract requires stopping, unconditionally, before doing anything else.
- **Why the CPU can't simply run as fast as the host allows** (@chapter(time-in-dosbox-x, short), §3.5): "as fast as possible" and "exactly up to the next scheduled deadline, no further" are different instructions, and only the second one satisfies the contract.

Read this way, the scheduler isn't a grab-bag of cooperating functions that happen to keep hardware timing plausible. It's a single invariant, enforced continuously, and `PIC_RunQueue()`, `PIC_AddEvent()`, `TIMER_AddTick()`, and `increaseticks()` are four different mechanisms for upholding the same one sentence from four different angles — sizing the next batch, inserting new deadlines without breaking the ordering the contract depends on, advancing the clock the deadlines are measured against, and pacing all of it to the one real clock available. Every implementation detail in this chapter is in service of that single guarantee.

## 4.14 The Complete Execution Path {#the-complete-execution-path}


Laid end to end, the path this chapter has followed is:

```
main()
  → DOSBOX_RunMachine()
    → Normal_Loop()
      → PIC_RunQueue()
        → CPU_Cycles computed
          → cpudecoder()
            → CPU stops (budget exhausted, or a callback fires)
              → next event fires, or the millisecond completes
                → back to PIC_RunQueue()
```

Every burst of execution is bounded by the scheduler before it starts. Ordering follows directly from §4.4 and §4.6: VGA retrace, DMA completion, sound IRQs, and serial byte arrival are all `PICEntry` instances in the same array, sorted by `index`, so which fires first depends only on that ordering. `CPU_CycleMax` also bounds how finely the scheduler can tell nearby deadlines apart: it sets how many discrete cycle positions are available to represent fractional-millisecond deadlines in, so a lower value gives the cycle-based execution budget fewer positions to approximate those deadlines with — a limit on the cycle representation, not on the fractional-millisecond deadlines the event queue itself stores.

What every single pass through that path guarantees — the chapter has largely left the reader to infer these along the way:

```
┌────────────────────────────────────────────────────────────────────────┐
│                    MAIN LOOP INVARIANTS                                 │
├────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  1. Every expired event is dispatched before any further CPU cycles    │
│     execute in that millisecond. (§4.4, step 2, runs before step 3.)   │
│                                                                          │
│  2. CPU execution is not intentionally allowed to advance past the     │
│     next scheduled event's deadline — §4.13's contract, mechanically   │
│     enforced by the batch size §4.4 computes and by §4.9's batch-      │
│     shrink on enqueue.                                                 │
│                                                                          │
│  3. Events with equal deadlines have a deterministic dispatch order    │
│     within the queue: it is determined by their `index` and insertion  │
│     order (§4.6) rather than by incidental list traversal order.       │
│                                                                          │
│  4. Guest time never skips a scheduled event: `TIMER_AddTick()` (§4.10)│
│     advances `PIC_Ticks` by exactly one millisecond at a time, and     │
│     `PIC_RunQueue()` is re-consulted every single time the budget      │
│     changes — there's no path from "time has advanced" to "the next    │
│     iteration" that doesn't pass back through the queue.               │
│                                                                          │
└────────────────────────────────────────────────────────────────────────┘
```

Ownership follows the same shape as everything else in this chapter, and it's worth stating plainly rather than leaving it to be inferred from which file each function happened to live in:

```
PIC (src/hardware/pic.cpp)          CPU (interpreter / dynamic core)
   owns: event timing, ordering,        owns: instruction execution,
   and cycle-budget calculation         guest register/memory state

                    \                  /
                     \                /
                       Normal_Loop()
                  coordinates execution,
                  dispatch, and host pacing
```

The PIC subsystem determines the event deadline and CPU budget; the CPU executes within that budget; `Normal_Loop()` coordinates the handoff between them and handles the surrounding host/timing control flow.

## 4.15 Busy Waits, and Why DOSBox-X Doesn't Melt Your Laptop {#busy-waits-and-why-dosbox-x-doesnt-melt-your-laptop}


One more question this structure answers: why doesn't a DOS busy-wait necessarily pin the host CPU at 100%? A huge amount of DOS-era code polls hardware with no yield instruction at all. As discussed in @section(time-in-dosbox-x/why-guest-time-cannot-simply-follow-wall-clock-time, short) (Chapter 3 §3.5), DOS busy-wait loops — such as the VGA retrace polling pattern — consume the CPU budget on every pass, but each pass through the scheduler hands the decoder only a bounded number of cycles.

```asm
wait_retrace:
    mov dx, 3DAh
    in  al, dx
    test al, 08h
    jz  wait_retrace
```

On real hardware the same loop consumes the CPU continuously; under a single-tasking DOS environment there may be nothing else competing for that CPU time. Under emulation, the guest is executing continuously from its own perspective, consuming the CPU budget on every pass through the decoder, but that loop is still just guest code running inside `(*cpudecoder)()`, and §4.4 already established that it's only ever handed a bounded number of cycles before control returns to the scheduler. Once a full millisecond is accounted for, `increaseticks()` (`src/dosbox.cpp`) — the same real-time gate §4.11 traced — checks whether any new host time has actually elapsed. When it finds none, it yields the host thread via `wrap_delay(1)` (a thin wrapper around `SDL_Delay()`) so the emulator doesn't pin the host CPU while waiting — the full host-yield behavior, including the `sleep1count` counter (which lets the first few idle passes actually sleep rather than spin, before the randomized pattern takes over) and the randomized sleep pattern used to avoid platform sleep-granularity resonance, is covered in @section(time-in-dosbox-x/keeping-the-simulation-synchronized, short) (Chapter 3 §3.9).

The guest does not directly observe the host sleep; from the guest's perspective, execution simply resumes when the emulator advances the next portion of simulated time. The host, watching from outside, sees a process that — when the emulator is ahead of host time — can spend much of its time yielding through `SDL_Delay()` and waking periodically to perform another bounded slice of guest work. Set `cycles=` very high with auto-adjust disabled and more of that millisecond shifts into the CPU path before `increaseticks()` is ever reached — which can increase host CPU utilization and power consumption compared with a fixed, period-appropriate cycle count.

```cpp
if (ticksNew <= ticksLast) {
    ticksAdded = 0;
    if (!CPU_CycleAutoAdjust || CPU_SkipCycleAutoAdjust || sleep1count < 3) {
        wrap_delay(1);
    } else {
        // small randomized sleep pattern to avoid resonance with
        // platforms whose sleep granularity always rounds to 1 ms
        ...
    }
    ...
    return;
}
```

A good way to see this firsthand: build a debug build and add a `LOG_MSG` inside `PIC_AddEvent` printing `handler` (as a function pointer — `addr2line` or your build's map file resolves it) alongside `delay`. The 18.2 Hz derivation belongs with the PIT hardware itself, not here: §4.10 notes that the one-millisecond internal tick is an emulator timing abstraction, and the relationship between that tick and the PIT's 18.2 Hz interrupt rate — including the historical reasoning behind IBM's divisor choice — is deferred to @chapter(dma-and-pit). Likewise, §4.11 covers DOSBox-X's own Turbo/fast-forward option — the `ticksLocked` bypass — but not the thing it's named after: the real, physical Turbo button, a case-front switch on real PC clones that solved a related but historically distinct problem, and which also belongs with the 8253/8254 PIT hardware in @chapter(dma-and-pit).

This chapter is where the two before it converge. @chapter(what-is-dosbox-x) and @chapter(dosbox-x-architecture) described the emulator's structure — what pieces exist, and how they're allowed to talk to each other. @chapter(time-in-dosbox-x) introduced its three notions of time — host wall-clock time, guest simulated time, and CPU execution budget — and how the last two are kept honest against the first. Neither chapter, on its own, explained how those pieces actually cooperate during a single moment of execution. This one did: the scheduler determines when control passes between CPU execution and a due event's handler, by enforcing the one contract §4.13 named; the CPU receives a bounded execution budget sized against that contract, never an open-ended license to run; and control repeatedly alternates between guest execution and event dispatch, one bounded slice at a time, for as long as the emulator runs. With that execution model in hand, the remaining chapters can examine individual subsystems — the CPU cores, the PIC and PIT themselves, VGA, sound, DMA — each one now placeable within the same scheduling framework traced here, rather than as an isolated block of behavior with no stated relationship to when it actually runs.
